# Protected Core machine authentication

Source implementation only; installs/builds/tests/runtime/issuer provisioning remain parent-window work. Vendor versions unchanged.

## Distinct boundaries

OCPI partner traffic keeps OCPI Token authentication using the partner-issued credentials token. OCPI Core commands use a separate protected CORE_INTERNAL/OCPI service credential, role evyar-ocpi, scope citrineos:ocpi:invoke, audience citrineos-core. Generic UI Core traffic uses CORE_INTERNAL/OPERATOR, role evyar-operator, scope citrineos:operator:invoke and the same Core audience. No shared admin principal, default tenant, browser service JWT or localBypass. Parent IAM provisions numeric Core tenant grants; requests cannot self-authorize a tenant. Product UUID tenant_id is not substituted for core_tenant_id.

New Base CoreMachineTokenProvider posts the supported camelCase JSON grant, validates returned issuer/audience/subject exactly matching configured clientId/expiry/service actor/core tenant/exact role and scope claims, bounds response size/deadlines and caches within an immutable config/principal instance per tenant. Core verifies signature/JWKS. Already-aborted waits observe pending rejections before throwing; both timer signals and elapsed wall time enforce fetch/body completion deadlines even when the event loop delays a timer. Token acquisition is single-flight per tenant; expiry margin is30s and caches/in-flight tenant maps are capped256. Separate configs/credentials do not share a token. Only an explicit401 permits one refresh/replay; timeouts, network errors,403 and ambiguous POST outcomes never replay. Errors omit response bodies/options/credentials. Credential rotation requires a new config/provider instance (normal process restart).

## OCPI configuration

Both local and Docker env factories select machine auth when OCPI_CORE_TOKEN_URL is set. Supply server-only OCPI_CORE_TOKEN_URL, OCPI_CORE_URL (trusted Core origin), OCPI_CORE_CLIENT_ID, OCPI_CORE_CLIENT_SECRET, OCPI_CORE_ISSUER, optional OCPI_CORE_AUTH_TIMEOUT_MS (default5000, max30000). The config schema exposes commands.coreAuth for configured deployments too. Audience/role/scope are fixed at the OCPI boundary; environment cannot elevate them. COMMANDS_CORE_HEADERS can contain non-auth headers; Authorization/proxy auth/cookies/host/API/admin secrets are rejected with machine auth. Existing explicitly selected upstream client-header path remains available when machine auth is absent; do not use it as a static expiring-JWT production workaround.

Common send boundary derives positive numeric tenantId from authenticated TenantPartner, checks any related Tenant.id and command query tenant agree, and attaches a just-in-time token. All1.6/2.x start/stop/unlock handlers share the boundary. Parent Core evyar-ocpi policy must permit only matching ocpp.evdriver remoteStartTransaction/remoteStopTransaction/requestStartTransaction/requestStopTransaction/unlockConnector routes. Partner callbacks and OCPI Token auth remain separate.

## Generic UI server transport

Bake NEXT_PUBLIC_AUTH_PROVIDER=generic, NEXT_PUBLIC_CORE_TRANSPORT=server and the existing NEXT_PUBLIC_TENANT_ID into the UI image. Runtime requires the same public settings and OPERATOR_CORE_TENANT_ID exactly matching that fixed positive numeric public tenant; there is no tenant1 fallback. Supply server-only OPERATOR_CORE_URL (origin only), OPERATOR_CORE_TOKEN_URL, OPERATOR_CORE_CLIENT_ID, OPERATOR_CORE_CLIENT_SECRET, OPERATOR_CORE_ISSUER, NEXTAUTH_URL (public origin only), NEXTAUTH_SECRET, configured generic login credentials OPERATOR_ADMIN_EMAIL/OPERATOR_ADMIN_PASSWORD (supported ADMIN_EMAIL/ADMIN_PASSWORD fallback remains). Build variables contain no machine secrets. If standalone Next constructs internal request URLs behind the reverse proxy, set server-only OPERATOR_REQUEST_ORIGIN to that exact internal origin; the browser Origin must still match public NEXTAUTH_URL, and no forwarded-host header selects Core or changes tenant grants. Parent does not need new Keycloak infrastructure or a password grant.

CredentialsProvider validates configured nonempty server credentials, returns server-assigned operator/admin session roles, and callbacks retain them in signed NextAuth session state. Browser localStorage roles never authorize proxy requests. Generic server mode uses the real server session and does not request /dev/token or /dev/roles, save service tokens, or accept a tokenless local user as a server login. Middleware no longer exempts generic auth; unauthenticated proxy requests receive401. Existing Keycloak client auth remains selected explicitly and retains its user access-token path.

BaseRestClient chooses same-origin /api/core for generic server transport. The proxy checks session and trusted admin/operator role, same public origin/CSRF origin, exact method/path allowlist from current UI callers, query allowlist, fixed query/body/nested tenant identity and repeated parameters. Browser cannot select host/grant/role/scope or provide an arbitrary callback/upstream URL. No browser Authorization/cookies/Host are forwarded. The body is capped256KiB, upstream response1MiB, total proxy deadline10s; M2M auth/request is bounded and redirects are errors. Core success JSON envelopes/status are preserved, rejected status is retained with a sanitized standard error envelope. No destructive financial/history route is allowed.

Parent evyar-operator policy must cover the existing UI permissions in apps/operator-ui/src/lib/utils/permissions.ts plus permissions/user, exactly the routes in lib/server/core-proxy.ts (configuration, driver, monitoring, reporting, certificate/transaction status commands, station-password/network-profile management and disconnect). This service role is distinct from the server-session symbolic admin/operator role. Generic Core proxy is not Hasura authentication. Preserve the existing supported Hasura user/service-header configuration separately; never substitute the operator Core service JWT for Hasura.

## Hasura service-header prerequisite

Both OCPI local/Docker factories now read optional server-only OCPI_GRAPHQL_HEADERS as a JSON object of string header values. No default admin secret, role or tenant header is injected. Nonobject/nonstring/invalid/case-duplicate headers are rejected with a sanitized message; configured values are preserved exactly. GraphQL transport forwards only its supplied headers and sanitizes upstream exception bodies; OCPI logger adds header/client-secret masking. No outbound Core token enters the GraphQL client, and GraphQL credentials never enter Core headers.

Authentication initially discovers TenantPartner by incoming OCPI server token before tenant routing is known; versions/credential/partner and broadcaster queries span configured tenants. A fixed tenant-scoped default token would hide other tenants and is not a supported multi-tenant discovery solution. Deployment must supply an existing supported internal Hasura credential/role with reviewed privileges for the actual OCPI discovery/read/write surfaces, and retain per-query ownership plus partner routing checks. This change adds no admin privileges or role widening. Parent owns the exact Hasura service grants and partner-isolation acceptance. Standalone source also lacked this env-header wiring; this is an explicit protected-Hasura prerequisite, not evidence about prior deployed authentication. No actual deployment/service headers were observed or printed.
