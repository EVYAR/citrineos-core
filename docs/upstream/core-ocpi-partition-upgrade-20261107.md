# Coordinated Core/OCPI partition notifications

Source prepared on the isolated core-apps regression branch. This document is not database acceptance.

Core migration `20260818120000-partition-transactions.ts` renames Transactions and five children to `_old` and creates partition parents. PostgreSQL keeps existing OCPI triggers attached to the renamed relations. Running already-recorded OCPI migrations again does not recreate them. Migration `20261107185250-notify-transaction-partition-identity.ts` updates a function only and cannot fix that binding gap.

New additive OCPI migration `20261107210000-restore-partition-notification-bindings.ts` binds exactly TransactionNotification (AFTER INSERT OR UPDATE, ROW, TransactionNotify) and MeterValueNotification (AFTER INSERT, ROW, MeterValueNotify) on the current public parents. A single transaction locks both parents; missing trigger functions or unexpected existing bindings fail closed. Existing standard triggers retain their OIDs and definitions. It neither changes functions nor modifies archived tables or data. Down is intentionally a no-op: binding provenance is unavailable, so deleting a binding could remove one that worked before the repair. The original OCPI migrations retain ownership of teardown. Undoing this repair in the CLI removes its ledger entry but retains the functional bindings; rerunning up validates them.

The other historical OCPI notification bindings are ChargingStations, Tariffs, Evses, Locations and Connectors. The later ConnectorTouchEvse/EvseTouchLocation triggers also target Connectors/Evses. None of these relations is replaced by Core's OCPPMessages or Transactions partition migrations. TransactionEvents, StartTransactions, StopTransactions and ChargingNeeds have no OCPI notification bindings in the audited migration set. No additional repair surface was found.

Both app .sequelizerc files select dist/migrations without a custom ledger table; both sequelize bridge configurations use the shared Core database. Normal sequelize-cli therefore stores both components' actual migration names in public.SequelizeMeta. Core readiness must preserve and classify the OCPI rows rather than demand equality between the full ledger and active Core filenames. Retired Core rows and OCPI rows are different provenance classes; neither permits synthetic history, aliases or rewriting.

## Paired fixture contract

`apps/ocpp-server/test/runtime/core-ocpi-upgrade.cjs` reuses the existing owner grant, resource guard, unique database names/comments, quiescence checks and ownership-restricted cleanup from database-fixture.cjs. No current grant is reusable. The parent must build current Core and OCPI migration outputs and freshly build DAL before the separate nullable Connector.timestamp runtime case. The existing upgrade-and-receipts.cjs already contains that fresh actual database read; it remains required and unexecuted for this source revision.

After a new parent window, run the paired fixture with the parent Node24 wrapper and `CORE_RUNTIME_LOCAL_GRANT` pointing to the new private grant. The parent supplies its bounded process/heap/cgroup checks; this fixture does not launch a service or acquire a grant. It creates only owned synthetic databases. On failure it leaves those owned databases for diagnosis; parent ownership checks remain necessary for cleanup.

Fresh lane: actual current Core CLI migrations; current OCPI CLI prefix excluding the new repair (byte copies of actual compiled outputs); snapshot working standard triggers; full current OCPI CLI discovery; verify first up preserves binding OIDs. Upgrade lane: actual 52 frozen Core fork migrations; seven byte-verified original OCPI migrations at `8326909087ed7c56f2d0d77cf5e29f09defa35f3:migrations`; current Core CLI; verify historic bindings moved to `_old`; current OCPI CLI. No original OCPI body is patched. The existing frozen Core dependency interoperability facade remains documented by database-fixture.cjs; this is migration-source acceptance using installed dependencies, not execution of an old application artifact.

The private result.json contains pairedOcpiProof schemaVersion 1, oldOcpiCommit, historicalOcpiMigrations, activeCoreMigrations and activeOcpiMigrations with sourcePath/filename/sourceSha256/emittedSha256. Each lane includes database plus beforeCore/afterCore/afterOcpi/afterRepeat objects containing full queried ledger and trigger inventory. Fresh also includes beforeRepair. Upgrade beforeCore contains the actual 52+7 executed rows. Every earlier row must survive each forward boundary. Repeat CLI must leave the ledger identical. No history SQL writes are used by the fixture.

Each lane also records sqlRepair (working/repaired OIDs and executed cases) and notificationProof (microsecond witnesses and actual LISTEN payloads). Actual compiled repair up/down is invoked through Sequelize. Cases include repeat up, preservation by no-op down, atomic rollback when the second function is temporarily unavailable, disabled binding rejection, and restoration of functional bindings. Negative tests temporarily remove only a trigger and rename a function on the owned database; no table/data reset or cascade removal is used.

LISTEN cases insert and update current Transactions parents, then insert current MeterValues with matching transactionCreatedAt. They use the same numeric transaction ID in distinct monthly partitions and tenants, assert tenant/id/stationId/createdAt identity on both transaction operations, retain six-digit fractional seconds through database JSON, and assert one meter notification with exact composite transaction identity and matching tenant. Exact notification counts catch duplicate inherited triggers. This proves SQL notifications only; it does not prove a running OCPI subscriber's downstream session/CDR delivery.
