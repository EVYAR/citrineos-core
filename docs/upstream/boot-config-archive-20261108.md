# Legacy Boot configuration archival

`20260821120000-preserve-unmapped-boot-configs.ts` sorts between the existing authorization constraint migration and `20260821120000-update-boot-pk-id.ts`. The landed upstream Boot migration remains unchanged. A normal owner CLI applies the new pending migration even when later historical ledger entries already exist; no ledger aliases or manual applied rows are needed.

The current Boot model requires an integer ID and a unique, non-null station FK. A legacy string-key configuration with no station cannot fit that model. The additive migration transfers only unreferenced configurations with zero tenant-qualified station matches to `BootConfigMigrationArchive`. This administrative archive has no runtime model, Hasura exposure, or station/tenant FK: its evidence must survive subsequent runtime lifecycle changes.

The archive preserves every original column in its original PostgreSQL type, the full original row as `json` (including JSON lexical values), a column-name/type signature, original identity, reason, migration identifier, and archival time. In one transaction, the migration locks writers, refuses ambiguous station matches, checks `VariableAttributes.bootConfigId` regardless of tenant or FK presence, and discovers other inbound FKs through PostgreSQL catalogs. Referenced orphans are refused rather than cascading, nulling, or rewriting their relationships. Exact JSON-text comparisons verify both the typed archive copy and its original payload before the live row is removed. Valid configurations and their references remain for the unchanged upstream migration.

Rollback requires the legacy varchar-key Boot schema; undo the upstream Boot migration first when it has run. It refuses column/type drift, archive provenance or payload changes, and any identity collision. It inserts the typed original columns, verifies every restored payload and the row count, and removes the archive only within that successful transaction. Failed archival or rollback leaves its inputs intact. An existing archive is refused on a repeated legacy `up`, preserving evidence rather than replacing it. Already-converted integer-ID schemas are left unchanged. A fresh legacy schema creates an empty archive and follows the same upstream migration path.

The source-only regression suite is `packages/dal/test/migrations/boot-config-archive-integration.test.ts`. It covers PostgreSQL JSON duplicate keys and numeric lexical values, microsecond timestamps, exact direct rollback, the real upstream Boot up/down and valid FK mapping, runtime FK rejection, untracked/cross-tenant references, cascading inbound FKs, ambiguous stations, tenant-qualified matching, empty/fresh and already-converted schemas, existing archives, restore identity collisions, and archive/schema tampering.

Validation: all 12 PostgreSQL cases passed on 2026-11-08, native exit 0, using a fresh separate restricted-role database on the exact-owned restore PostgreSQL container. The actual Core and IAM databases were not used by these tests. The guarded run declared 1024 MiB with a fixed 1536 MiB reserve. Evidence is retained outside Git in `control/dev-20261108/db-upgrade-focused-a1.private.log` and its source SHA-256 manifest. Native focused TypeScript compilation (migration, upstream dependency, test and fixture helper) also passed with the repository compiler settings under the same 1024/1536 guard. Scoped formatting and `git diff --check` passed. Full workspace build, full suite and actual restored Core migration continuation remain pending parent execution.

For this guarded topology, `BOOT_ARCHIVE_FIXTURE_FILE` selects a private, canonical, owner-only JSON grant. Its strict schema requires a unique `boot_archive_fixture_<16 hex>` database and matching restricted role, random password, marker, expiry, exact Docker container identity/label/cap and sole-member internal network/private bridge IP. The helper verifies live Docker state before connecting, then the database marker, owner and non-superuser/non-createdb/non-createrole/non-replication role before every destructive test reset. An invalid explicit grant fails closed without falling back to container creation. Normal CI creates a disposable 256 MiB PostgreSQL container with a random password.

The original actual-restore failure and its 60-row ledger/545-witness anchor remain separate evidence. After review and a new execution window, the same partially upgraded copy can run the normal owner CLI without repeating its already-recorded message conversions.
